# Pabrikon

Pabrikon is a Python CLI toolkit for developing Linux icon themes. It creates
and validates projects, renders SVG sources into theme assets, manages aliases,
optimizes SVG files, and packages completed themes. It can be used manually with
an existing icon-theme repository, but automatic project adoption and layout
normalization are still planned. Aliases use `data/aliases.toml`; bundled legacy
CSV alias tables and their management commands have been removed.

## Requirements

- Python 3.12 or newer
- `rsvg-convert` from librsvg to render PNG icons
- `svgcleaner` to optimize SVG icons

Install Pabrikon from the repository root:

```bash
./install.sh
```

The installer requires Python 3.12 or newer and installs Pabrikon into a
user-owned virtual environment under `~/.local/share/pabrikon`, with the
`pabrikon` command linked from `~/.local/bin`. It does not use `sudo` or edit
shell startup files. If prompted, add `~/.local/bin` to your `PATH`. Override
install locations with `PABRIKON_HOME` and `PABRIKON_BIN_DIR` environment
variables. To install with pip instead, run `python3.12 -m pip install .`.

For development and tests:

```bash
python -m pip install -e ".[dev]"
pytest
```

See [CONTRIBUTING.md](CONTRIBUTING.md) for system dependencies, all CI checks,
and the Linux Docker development environment. macOS development has not been
verified; Docker is available as a Linux-based option.

The end-to-end acceptance test also needs `rsvg-convert` (librsvg) and
`svgcleaner`; it is skipped when either executable is unavailable. CI installs
both tools and runs the full suite, Ruff, mypy, and a wheel build.

## Quick start

Initialize a theme project, add SVG files under a context's `scalable/`
directory, then validate, and build it:

```bash
pabrikon init my-theme
cp firefox.svg my-theme/icons/apps/scalable/
cd my-theme
pabrikon validate
pabrikon build
pabrikon package
```

`pabrikon build --dry-run` previews planned outputs. `pabrikon optimize`
creates optimized copies under `dist/optimized/icons/` and preserves source
files by default. `--in-place` replaces source SVGs only after each optimized
file passes validation. `pabrikon clean` removes generated files from `build/`
and never removes the source tree.

### Try the complete workflow

This creates a small theme and runs the main workflow. Install `rsvg-convert`
and `svgcleaner` first; `optimize` requires the latter.

```bash
pabrikon init demo-theme
mkdir -p demo-theme/icons/apps/scalable
cat > demo-theme/icons/apps/scalable/example.svg <<'SVG'
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 16 16">
  <rect width="16" height="16" fill="#369" />
</svg>
SVG
pabrikon validate demo-theme
pabrikon build demo-theme
pabrikon optimize demo-theme
pabrikon package demo-theme
pabrikon clean demo-theme --dry-run
```

The `clean` preview lists generated files without removing them. To remove the
build output after reviewing the list, run `pabrikon clean demo-theme`.

## Recommended theme project layout

```text
my-theme/
├── README.md
├── LICENSE                       # Optional; preserve upstream license files
├── index.theme                   # Theme metadata generated from the config
├── icons/                        # Editable source assets
│   ├── actions/
│   │   └── scalable/
│   ├── apps/
│   │   └── scalable/
│   │       └── firefox.svg
│   ├── categories/
│   │   └── scalable/
│   ├── devices/
│   │   ├── scalable/
│   │   └── 16/
│   │       └── auth-sim.svg        # Optional fixed-size SVG source
│   ├── places/
│   │   └── scalable/
│   └── status/
│       └── scalable/
├── data/
│   ├── pabrikon.toml              # Project, theme, and build settings
│   └── aliases.toml              # Optional symbolic icon aliases
├── build/                        # Generated by `pabrikon build`
│   ├── index.theme
│   └── apps/
│       ├── scalable/
│       │   └── firefox.svg
│       └── 48x48/
│           └── firefox.png
└── dist/                         # Packages and optimized copies
    ├── optimized/
    │   └── icons/
    └── my-theme-1.0.0.tar.gz
```

The tree shows a project after adding an icon and running build, optimize, and
package. A fresh project does not yet contain `build/` or package output.
`pabrikon init` creates the configured source context directories, each with a
`scalable/` folder. Put original SVGs in `icons/<context>/scalable/`; Pabrikon
keeps generated assets in `build/`, separate from editable sources. Contexts
and raster sizes are controlled by `data/pabrikon.toml`. Sources in any
directory declared by `index.theme` are supported; the directory's `Type` and
`Size` control raster outputs, while `svg` format preserves the source SVG at
the same relative directory.

## Project configuration

`pabrikon init` writes `data/pabrikon.toml`. Edit its project and theme metadata,
enabled icon contexts, generated formats, and raster sizes there. For example:

```bash
pabrikon config edit
pabrikon config edit . --editor nano
```

The edit command opens an existing configuration in a terminal editor, selected
from `--editor`, `$VISUAL`, `$EDITOR`, `vim`, then `nano`. It opens the file
without parsing it first, so you can repair invalid TOML. If the file is
missing, run `pabrikon init` to create it.

```toml
[project]
name = "my-theme"
version = "1.0.0"
description = "A custom Linux icon theme"
license = "GPL-3.0"

[theme]
name = "My Theme"
comment = "A custom Linux icon theme"
inherits = ["Adwaita"]

[build]
sizes = [16, 24, 32, 48, 64, 128, 256]
formats = ["svg", "png"]

[build.directories]
enabled = ["apps", "categories", "devices", "places", "status"]

[validation]
strict = false
```

Sources go in `icons/<enabled-context>/scalable/<name>.svg`. The default
formats are scalable SVG and PNG; configured sizes apply to PNG outputs.
`validation.strict = true` treats validation warnings as errors. Icon names
must start with a letter or digit and may also contain `.`, `_`, `+`, `@`, or
`-`.

## Icon aliases

Aliases are optional. Define them in `data/aliases.toml`, with one TOML table
per destination icon context. A value without `/` refers to an icon in the
same context; `context/name` refers to an icon in another enabled context.
Targets must match source SVGs under `icons/`.

For example, if `icons/apps/scalable/firefox.svg`,
`icons/places/scalable/user-home.svg`, and
`icons/apps/scalable/accessories-calculator.svg` exist:

```toml
[apps]
web-browser = "firefox"

[places]
folder-home = "user-home"

[categories]
applications-mathematics = "apps/accessories-calculator"
```

The example adds two aliases within their own context and one cross-context
alias. During `pabrikon build`, Pabrikon creates relative symbolic links for
each configured output format and raster size in `build/`; it does not alter
the source SVGs. To preview or rebuild just the links after a build, use:

```bash
pabrikon aliases edit
pabrikon aliases build --dry-run
pabrikon aliases build
pabrikon list aliases
```

`pabrikon aliases edit` opens `data/aliases.toml` in the selected terminal
editor. It uses the same editor selection as `pabrikon theme edit`: `--editor`,
`$VISUAL`, `$EDITOR`, `vim`, then `nano`. If the alias file is missing, the
command creates it with a commented example template before opening it.

Validation reports missing targets, cycles, aliases that shadow real icons,
and aliases in contexts that are not enabled in `data/pabrikon.toml`.

### Use Pabrikon with an existing icon theme

Preview adoption from an existing local checkout before applying it:

```bash
pabrikon init --from "$PWD/upstream-theme" --dry-run
pabrikon init --from "$PWD/upstream-theme" --apply
```

When a checkout contains multiple themes, use `--theme-root` with a detected
repository-relative path. For a remote project, provide the URL and clone
directory explicitly:

```bash
pabrikon init --from https://github.com/BlankOn/tebu-flat.git \
  --target "$PWD/tebu-flat" --ref master --dry-run
pabrikon init --from https://github.com/BlankOn/tebu-flat.git \
  --target "$PWD/tebu-flat" --ref master --apply
```

Adoption reads the selected theme's `index.theme`, proposes
`data/pabrikon.toml` and copies each recognized SVG to the matching directory
under `icons/`, following the selected theme's `index.theme`. For example,
`devices/16/auth-sim.svg` and `devices/64/auth-sim.svg` remain in those
directories. The build writes SVGs to those same relative directories and
renders PNGs into the declared fixed-size directories; a fixed-size source
takes precedence over a scalable source when both provide the same icon and
size.
Original files, metadata, license files, and
unrecognized assets remain in place. The report identifies alternate metadata,
submodules that were not initialized, ignored paths, and filename collisions.
Use `--verbose` or `--json` to inspect every ignored path and collision. Files
whose names collide in the v2 layout are all skipped; aliases that target those
ambiguous icons are skipped too, while unambiguous assets can still be adopted.
Unsafe destination paths stop the operation without writing the project config.
The generated config uses `license = "UNKNOWN"`; review the upstream license
and set the correct SPDX identifier manually before packaging. Existing
Pabrikon configuration requires `--regenerate-config`, which keeps a `.bak`
copy.

Recognized SVG symlinks whose targets resolve to adopted source icons are
proposed as aliases in the dry-run report and written to
`data/aliases.toml` with `--apply`. Broken, cyclic, escaping, unsupported, or
ambiguous links are reported for manual review. If `data/aliases.toml` already
exists, adoption leaves it unchanged and reports the proposed aliases instead.
Symlinks are never rewritten or removed.

Remote dry-run explicitly clones the selected URL to `--target` so Pabrikon can
inspect its files. Re-running the same command with `--apply` reuses that clone.
Submodules are not initialized, Git hooks and configured filters are disabled
for cloning, and repository scripts are never run. Raster assets, HiDPI
variants, and layouts without a recognized SVG source are listed for manual
review rather than converted or guessed.

Scalable folders are recognized from `index.theme` sections, so a literal
`scalable/` folder is not required when metadata marks a context folder such as
Citropy's `apps/` as scalable. KDE Breeze generates `index.theme` during its
own CMake build; prepare that theme root before adoption. These upstream
layouts remain acceptance fixtures, so review the dry-run report before
applying.

Review `[build.directories].enabled` and the theme metadata in
`data/pabrikon.toml`. If you want to regenerate an existing root `index.theme`
from that configuration, explicitly run `pabrikon theme init "$THEME_ROOT"
--force`; this replaces the existing metadata file. Otherwise, edit the file
directly with `pabrikon theme edit "$THEME_ROOT"`. Then check and build the
prepared project:

```bash
pabrikon validate "$THEME_ROOT"
pabrikon build "$THEME_ROOT"
pabrikon package "$THEME_ROOT"
```

Inspect the generated `build/` tree and package before deciding whether to
remove or reorganize any upstream files. Automated repository analysis and
safe layout normalization remain planned, as described in the PRD.

## Commands

```text
pabrikon init [TARGET] [--name NAME]
pabrikon init --from SOURCE [--theme-root PATH] [--dry-run|--apply]
pabrikon init --from GIT_URL --target DIRECTORY [--ref REF] [--dry-run|--apply]
pabrikon config edit [PATH] [--editor EDITOR]
pabrikon validate [PATH]
pabrikon build [PATH] [--all] [--size N] [--sizes N,N] [--directory DIR] [--icon NAME] [--dry-run]
pabrikon clean [PATH] [--type build|png|svg|symlink] [--dry-run]
pabrikon aliases edit [PATH] [--editor EDITOR]
pabrikon aliases build [PATH] [--dry-run]
pabrikon optimize [PATH] [--dry-run] [--in-place]
pabrikon package [PATH] [--dry-run]
pabrikon info [PATH]
pabrikon list [icons|directories|aliases|generated] [PATH]
pabrikon theme init [PATH] [--force]
pabrikon theme show [PATH]
pabrikon theme edit [PATH] [--editor EDITOR]
pabrikon theme validate [PATH]
```

Run `pabrikon --help` or `pabrikon COMMAND --help` for details. Packaging
requires a successful build and valid generated outputs. `--force` on
`pabrikon theme init` allows replacing an existing `index.theme`.

`pabrikon theme edit` opens the project's root `index.theme` in a terminal
editor. Pabrikon selects the editor from `--editor`, then `$VISUAL`, `$EDITOR`,
`vim`, or `nano`. If `index.theme` is missing, it creates the file from
`data/pabrikon.toml` before opening it. For example:

```bash
pabrikon theme edit
pabrikon theme edit . --editor nano
```

`--editor` is also available on `pabrikon aliases edit`.
`pabrikon config edit` uses the same editor selection and only opens an
existing `data/pabrikon.toml`.

### Shell autocomplete

Pabrikon supports argument completion in Bash and Zsh through `argcomplete`.
After installing Pabrikon, add the matching line to your shell startup file:

```bash
# ~/.bashrc
eval "$(register-python-argcomplete pabrikon)"
```

```zsh
# ~/.zshrc
eval "$(register-python-argcomplete pabrikon)"
```

Open a new shell, or reload its configuration with `source ~/.bashrc` or
`source ~/.zshrc`. Completion includes registered commands, options, and
arguments with known choices, such as `pabrikon clean --type`.

All commands accept `--verbose`, `--quiet`, and `--json` (as well as `-v` and
`-q`). Verbose mode adds per-file details where available. Quiet mode suppresses
normal text while errors remain on standard error. JSON mode writes one
machine-readable value to standard output; command errors use an object with
`command`, `ok: false`, and an `error` message, and retain the command's normal
exit code. JSON output takes precedence over quiet mode. These options can be
placed before or after the command, including nested commands such as
`pabrikon theme show --json`.

`pabrikon validate` checks the TOML configuration, `index.theme`, source SVGs,
aliases, and existing generated files. `pabrikon build` also writes the
effective `index.theme` into `build/`, reuses outputs that are newer than their
sources, and creates configured aliases. Use `--all` to rebuild every output.
`pabrikon clean --dry-run` previews removal from `build/`; `--type png`,
`--type svg`, and `--type symlink` limit cleanup to those generated files.
`pabrikon optimize` writes optimized copies under
`dist/optimized/icons/` by default, leaving source files unchanged. Finally,
`pabrikon package` writes a deterministic `.tar.gz` under `dist/` after
checking the generated theme.

## Docker

Build the Linux test image and run the complete contributor checks (unit,
acceptance, lint, type check, and wheel build) as described in
[CONTRIBUTING.md](CONTRIBUTING.md). To run only pytest in the test image:

```bash
docker build -f Dockerfile.test -t pabrikon-tests .
docker run --rm pabrikon-tests
```

Build the CLI image and use it with a host project:

```bash
docker build -t pabrikon .
docker run --rm pabrikon --help
docker run --rm -v "$PWD/my-theme:/workspace" -w /workspace pabrikon validate .
```

## Development status

The current CLI includes project initialization, validation, building,
cleaning, alias generation, theme metadata, project information and listing,
SVG optimization, tar.gz packaging, and adoption of recognized existing icon
themes. Adoption can copy scalable SVGs and import safe SVG symlinks as aliases;
it remains partial while the documented repository fixtures and less common
layouts are being verified. TOML aliases have replaced legacy CSV aliases;
there is no automatic importer for external CSV mapping files. Browser preview
remains a roadmap feature.

### Freedesktop Icon Theme specification coverage

Pabrikon supports the core theme workflow, but it does not implement every
feature in the [Freedesktop Icon Theme Specification 0.10](https://specifications.freedesktop.org/icon-theme/0.10/).
Current limitations include:

- `index.theme` generation covers basic `Name`, `Comment`, `Inherits`,
  `Directories`, and generated `Fixed`/`Scalable` directories. Configuration
  and validation do not yet cover all metadata such as `Hidden`, `Example`,
  localized names/comments, `Threshold`, or every per-directory field.
- Pabrikon uses SVG sources and can emit SVG and PNG. It does not support XPM
  or the per-icon `.icon` metadata sidecar format.
- It does not implement desktop icon lookup, inherited-theme fallback
  resolution, theme installation, or icon-cache management. `Inherits` is
  written as metadata; Pabrikon does not resolve the inherited themes.
- Adopted `index.theme` directories preserve declared `Scale` values, including
  `@2x` and `@3x` paths, when planning SVG and PNG outputs. Pabrikon does not
  yet expose scale as a standalone project configuration option. This is a
  compatibility convention outside specification 0.10.

These gaps are recorded as future requirements in
[`docs/PRD/PRD-pabrikon.md`](docs/PRD/PRD-pabrikon.md#181-freedesktop-icon-theme-010-coverage).
